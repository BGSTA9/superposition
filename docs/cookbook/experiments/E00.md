## 1. Claim and pages

**The paper's claim (p. 2; bias behaviour p. 10; linear baseline pp. 10–13).** Take n = 5
features of decreasing importance and squeeze them into m = 2 hidden dimensions with the
*ReLU output model* x′ = ReLU(WᵀWx + b).

- **Sparsity S** is the probability that a feature is zero. *Importance* Iᵢ weights each
  feature's squared error in the loss.
- At S = 0 (dense), the two most important features get orthogonal dedicated dimensions. The
  other three are not embedded.
- At S = 0.8, the four most important features are stored as two *antipodal pairs* (two
  features on one line, pointing opposite ways).
- At S = 0.9, all five are embedded as a pentagon. That is *superposition*: more features than
  dimensions, at the cost of *interference*.
- The linear model x′ = WᵀWx + b never does this. It keeps the top m = 2 features at every S.

The paper does not state the importances for this figure. SPEC §3 fixes Iᵢ = 0.9ⁱ, which
reproduces it ([SPEC.md](../../../SPEC.md) §7 E00). **[Documented]**

### 4b. Doing it by hand

Each step: action → command → expected result → check → if it fails. **[Recommended]**

1. **Derive the linear optimum before training anything.** On paper, show that the best
   linear model keeps the top m features exactly and predicts the mean p/2 for the rest, so
   L* = Σ_{i≥m} Iᵢ(p/3 − p²/4) with p = 1 − S (`theory.linear_optimum_loss` docstring, p. 13).
   - Command (check your numbers against the repo's):

     ```bash
     uv run python -c "from superposition.data import geometric_importance; from superposition.theory import linear_optimum_loss; I = geometric_importance(5, 0.9); print([round(linear_optimum_loss(I, 2, p), 4) for p in (1.0, 0.2, 0.1)])"
     ```

   - Expected: `[0.1829, 0.1244, 0.0677]` (SPEC rounds to 0.183, 0.124, 0.068).
   - If yours differ: check that you sum over i ≥ m with features sorted by importance, and
     that the variance of one feature is p/3 − p²/4.
2. **Build the training grid as one batched model.** 3 sparsities × 8 restarts = 24 instances
   per model kind, each with its own p. Initialization of instance k depends only on
   (seed, k). Loss: sum over features, mean over batch, sum over instances.
   - Command: none; you write the code (rebuild kit M1–M3).
   - Expected: a single training loop, no Python loop over instances.
   - Check: `uv run pytest -c rebuild/pytest.ini rebuild/tests/test_train.py` once your
     skeleton is filled in (it fails with `NotImplementedError` until then).
   - If it fails: re-read CLAUDE.md "§3 pitfalls": Xavier per instance, never on the 3-D tensor.
3. **Pick the best restart per S on fresh samples.** Evaluate every instance on 100,000 fresh
   samples and keep the lowest loss per S.
   - Expected: at S = 0.9 most restarts reach 5 features, a few stop at 4 (cited run: 6 of 8
     and 2 of 8).
   - If the best restart is not a pentagon: you probably selected on the training loss or on
     too few samples.
4. **Write the acceptance checks before you look at your weights.** Use SPEC §7's table and
   D-106's readings: |cos| < 0.1 for "orthogonal"; angular gaps over all five directions with
   wrap-around; the bias check vacuous when no feature has ‖Wᵢ‖ < 0.05.
   - Check: hand-built geometries. An ideal pentagon must pass and a squashed one must fail,
     as `tests/unit/test_experiment_criteria.py` does.
5. **Run, and compare with the reference values, as sanity checks only.**
   - Command: `uv run superposition run intro_pentagon --profile quick --device cpu` for the
     repo's answer.
   - Expected: PASS 11/11; ReLU best losses about 0.183, 0.059, 0.021.
   - If S = 0.9 comes out near 0.0214 rather than 0.0196: that is what this repo gets too. Read
     §6 below before you suspect your code.
6. **Draw the arrows, canonicalized.** Rotate the most important feature to +y and reflect
   (D-109), then compare with the p. 2 figure.

## 6. What actually happened

1. **The S = 0.9 loss does not match SPEC's reference.** Ours is 0.0214 on 1,000,000 samples;
   SPEC's is 0.0196. ([phase-1.md](../../progress/phase-1.md) open issue 1.) What was checked,
   all as INFO rows of the cited run:
   - same geometry (norms ≈ 1.1, biases ≈ −0.21);
   - all 12 arrangements converge to 0.02142–0.02165;
   - a 20,000-sample estimate has 3.7% noise, and only 1 of 200 estimates reaches 0.0196;
   - SPEC's reference *linear* losses lie below the exact optimum, which no model can beat in
     expectation, so the reference values carry selection bias.

   [REPRODUCTION.md](../../REPRODUCTION.md) § E00. **[Documented]**
2. **Two statements were corrected by the review.**
   - R1-04: the arrangement diagnostic cannot rank the 12 arrangements; they span about 1%,
     twice the evaluation noise. An earlier claim that the best restart's arrangement was
     "already the best" was withdrawn.
   - R1-05: the explanation of 0.0196 is now labeled a hypothesis, with its probability (a
     few percent).

   ([REVIEW.md](../../REVIEW.md) R1-04, R1-05.) **[Documented]**
3. **Changed after results were seen (flagged).**
   - The D-107 diagnostics were added after the first run showed the gap. They are INFO rows;
     no criterion or threshold changed (D-107; S 35cab3f0 @ 08:39–08:42Z).
   - The `exact_loss` field was added after review R1-11. The grading still uses the sampled
     loss (`ce2dece`; R1-11 "The grading is unchanged").
   - SPEC's E00 criteria themselves were written after the planning conversation's
     verification run [Planning conversation, per owner]. Nothing in the repo shows whether
     any threshold was adjusted to that run; that is unknown.

   **[Documented]**
4. **Runs outside provenance.** The scratchpad scripts `pent.py` and `arrangements.py`, and
   the dirty-tree E00 runs moved aside before the cited runs, are not in `results/`. Their
   outputs are unknown. [S 35cab3f0 @ 2026-09-29T08:39Z–09:05Z] **[Documented]**
5. **Decisions:** D-101 (optimizer), D-103 (paired seeds: each ReLU instance starts from its

## 9. Explain it back

1. At S = 0.9 every bias is about −0.21 and every norm about 1.1. Why does a negative bias let
   the pentagon tolerate positive interference, and why can the linear model not use that
   trick?
2. The best-of-8 linear losses are slightly *below* the exact optimum. Why is that not a bug,
   and what does it say about reporting "the best restart's loss"?
3. Why does a 20,000-sample loss estimate have 3.7% relative noise for the S = 0.9 pentagon,
   when most samples have no active feature at all?

**Drill.** With the repo's engine, train only the S = 0.9 ReLU grid with 64 restarts. Pick the
best restart twice: once on 20,000 samples, once on 1,000,000. Does the chosen restart change?
How far below its own 1M-sample loss is the 20k-selected value? Predict the sign of the gap
before you run it. **[Recommended]**
